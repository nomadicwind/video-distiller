# Video Distiller 设计文档

**日期**：2026-08-20
**状态**：已评审，待实施计划

---

## 1. 概述

Video Distiller 是一个本地优先的游戏操作录像蒸馏工作台。

**输入**：游戏操作录像（上传、视频网站 URL、或本地采集）。
**输出**：一份分层的操作序列 IR，以及由它派生的流程文档、AHK 脚本、Razer 宏与可执行注入计划。

**核心命题**：视频里看不见键盘鼠标。分析师凭游戏经验在时间轴上分层标注自己的观察，Agent 负责跨层对齐、归纳结构、并用确定性匹配器自我验证，人做最终质量调优。

### 1.1 使用目的

1. **生成训练数据** —— 产出结构化的操作序列，供模仿学习或 Agent 评测使用。
2. **操作教学与流程沉淀** —— 把高手录像提炼成可复用的循环与方案。

### 1.2 运行环境

- **开发**：macOS 与 Windows 并行
- **运行时**：Windows（注入执行仅在 Windows 可用）
- **使用者**：单人本地使用
- **目标游戏**：一款（至多 2–3 款）固定游戏，第三方商业游戏，个人自用场景

### 1.3 游戏特性约束

目标游戏**自动锁敌**，操作不涉及走位与瞄准。因此：

- 坐标与位置在本阶段不是分析对象
- 分析价值集中在**技能顺序**与**时序节奏**
- 数据模型保留坐标结构以备将来扩展，但本阶段不启用相关交互与校验

## 2. 非目标

明确排除，不在本设计范围内：

- **画面识别（CV）**。Agent 不读画面、不推断游戏状态。所有观察由人提供。
- **自动判定重放正确性**。注入执行器只负责执行，成败由人肉眼判断。
- **可执行的循环条件**。循环的进出条件是人写的自然语言注释，不是可执行断言。
- **模拟操作模式**（跟着视频用真键盘敲）。已评估后排除。
- **多用户 / 云端 / 协作**。单人本地。
- **走位、瞄准、鼠标轨迹分析**。
- **UI 视觉设计**。本文档只定义布局结构与交互契约。

## 3. 核心概念：五层体系

| 层 | 名称 | 内容 | 产出方式 | 观察性质 |
|---|---|---|---|---|
| **L0** | 操作 Operation | 单击 / 长按 / 按键 / 键长按 / 滚轮 / 等待 | 人工标注，多 Take | **推断**（看不见键盘） |
| **L1** | 技能 Skill | 单个技能的释放 | 人工打点，多 Take | **直接观察**（看动画） |
| **L2** | 连招 Combo | 多步组合技能 | 人工打点（可选），多 Take | 直接观察 |
| **L3** | 循环 Rotation | L0–L2 的重复序列，可参数化 | Agent 提案 + 人编辑 | — |
| **L4** | 方案 Playbook | 多个循环与序列拼接成的完整打法 | Agent 提案 + 人编辑 | — |

### 3.1 关键认识：L1 比 L0 更可靠

视频里看不见键盘，所以 L0 标注是分析师**基于键位知识做的推断**（"火球飞出去了，那他应该按了 2"）。而 L1 技能是**直接看到的**（看动画效果）。

因此：

- **每一层都是独立的人工观察通道**，不是从 L0 自动推导上层
- **Agent 的核心任务是跨层对齐**（L0 ↔ L1 ↔ L2），而不是从 L0 匹配出 L1
- **Keymap 可以从对齐中反推**，不必预先填好

最后一条消除了系统最大的冷启动障碍：你不需要先把键位表填完才能开始标注。

### 3.2 L0 内部的两种表示

这是引擎实现细节，不是概念层级：

| 表示 | 内容 | 消费者 |
|---|---|---|
| **事件流** | `key_down` / `key_up` / `mouse_down` / `mouse_up` / `wheel` | 注入执行器 |
| **操作流** | `tap` / `hold` / `chord` / `wheel` / `wait`（含时长） | pattern 匹配器 |

两者由确定性的配对合并算法互转。**事件流严格保持原子**——不支持组合事件。组合的表达属于 pattern 层。

理由（不可妥协）：

1. 注入执行器消费的就是原子事件；L0 有组合就得在执行时展开，展开逻辑与匹配逻辑分居两处，必然不一致
2. 组合一旦进 L0 就要处理嵌套组合，匹配器与校验器复杂度爆炸

### 3.3 L1 与 L2 在数据模型中是同一实体

技能与连招只按 `len(pattern)` 区分显示，不建两套结构。

## 4. 系统架构

```
┌───────────────────────────────────────────────────────┐
│ 浏览器 UI  (React + TypeScript + Vite)                 │
│  ├ 帧级视频播放器（0.25× / 0.5× / 1×，逐帧步进）         │
│  ├ 缩略图带 + 片段圈选                                  │
│  ├ 泳道时间轴标注编辑器（L0–L2，可折叠）                  │
│  ├ 打表计时工具条                                       │
│  ├ 块编辑器（L3 / L4）                                  │
│  └ Agent 会话面板 · 导出预览 · 执行控制台                 │
└────────────────────┬──────────────────────────────────┘
                     │ HTTP + WebSocket
┌────────────────────▼──────────────────────────────────┐
│ 内核后端  (Python 3.11 + FastAPI)                      │
│  ingest   视频摄取：本地上传 / URL 拉取 / 触发采集         │
│  media    解帧、缩略图带、时间码 ↔ 帧号换算               │
│  store    项目·视频·Analysis·泳道·Take·IR 持久化          │
│  ir       IR 模型定义、校验、层间对齐、版本快照            │
│  agent    跨层对齐 / 循环发现 / 方案编排                  │
│  emit     导出后端：md · ahk · razer · plan              │
└────────────────────┬──────────────────────────────────┘
                     │ HostAdapter (本地 IPC / 子进程)
┌────────────────────▼──────────────────────────────────┐
│ 平台宿主  WindowsHost │ MacHost │ MockHost             │
│  capture_screen()   录屏 → 视频文件（双平台）             │
│  inject_input()     键鼠注入（仅 Windows）               │
└───────────────────────────────────────────────────────┘
```

### 4.1 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 内核 / 后端 | Python 3.11 + FastAPI，uv 管依赖 | 视频解码、序列算法、LLM SDK 生态齐全；mac/Win 行为一致 |
| 前端 | React + TypeScript + Vite；`<video>` + WebCodecs 帧级 seek；canvas 标注层 | 浏览器是做时间轴标注最成熟的平台，双平台零差异 |
| 存储 | SQLite（结构化数据，IR 以 JSON 列存 + 关键字段索引）+ 文件系统（视频源、抽帧缓存） | 单用户本地场景足够；备份即拷贝一个目录 |
| 平台层 | `HostAdapter` 接口 × 3 实现 | 见 4.3 |

具体库选型（解帧库、时间轴组件、状态管理方案）留到实施计划阶段决定。

**打包**：初期不打包，`uv run` + `pnpm dev`。将来若需单文件分发，用 Tauri 包一层（比 Electron 轻，Rust 侧适合写 Windows 注入）。

### 4.2 模块边界约束

这些约束决定了系统后期能不能改得动：

- `media` 只回答"给我时间码，还你帧"——不知道标注存在
- `ir` 是纯数据结构 + 校验器——不知道 UI、Agent、导出存在
- `agent` 签名为 `IR → Proposal`，纯函数式——可脱离前端跑测试，可对同一输入反复试不同 prompt，**失败无副作用**
- `emit` 每个后端一个独立文件，签名 `IR → bytes`——新增一种宏格式 = 新增一个文件，不碰其他代码
- `HostAdapter` 是**全系统唯一平台相关的地方**

### 4.3 HostAdapter 三实现

| 实现 | `capture_screen()` | `inject_input()` |
|---|---|---|
| **WindowsHost** | ffmpeg `ddagrab` / OBS WebSocket | AHK v2 子进程（起步），不足则 Interception 驱动 |
| **MacHost** | ffmpeg `avfoundation` | 不实现 |
| **MockHost** | 返回预置视频 | 记录调用，不实际注入 |

MockHost 保证全链路在 macOS 上可开发、可测试。

### 4.4 数据流

```
视频源 ──ingest──▶ 媒体库 ──▶ Analysis
                                     │
                    ┌────────────────┼────────────────┐
                 L0 泳道           L1 泳道          L2 泳道
                （多 Take）       （多 Take）       （多 Take）
                    └────────────────┼────────────────┘
                                     │  ◀── Segment 圈定作用范围
                                     ▼
                              Agent 推断阶段
                    （聚合 → 对齐 → 补区间 → 归纳 → 验证）
                                     ▼
                        L3 循环提案 + L4 方案提案
                                     │
                                 人工裁决与编辑
                                     │
                                   emit
              ┌───────────┬──────────┼──────────┐
              ▼           ▼          ▼          ▼
         流程文档     AHK 脚本   Razer 宏    注入执行
                                              │
                                       执行日志回灌为 Take
```

**IR 是唯一的中心资产。** 视频是它的证据，脚本是它的投影。丢了脚本可以重新导出，丢了 IR 就得重标。因此 IR 版本化快照：每次 Agent 加工前存一版，人工纠错可回滚。

## 5. 数据模型

### 5.1 实体层级

```
Project (一款游戏)
 ├ SkillCatalog             技能 / 连招定义（可为空，边标边长）
 ├ Keymap[]                 职业级键位映射（可为空，可反推）
 ├ Video[]                  源视频 + fps / 分辨率 / 来源
 ├ Analysis[]               命名自动生成：video-1_profile-x_v1
 │   ├ video_ref, profile_ref, version
 │   ├ Segment[]            圈选区间；不圈则默认全片
 │   └ Lane[]               泳道，每层一条（L0 / L1 / L2）
 │       └ Take[]           同一泳道的多次独立标注
 │           └ marks[]      point mark 或 span mark
 ├ Rotation[]               L3：跨 Analysis 提炼出的循环
 └ Playbook[]               L4：跨 Analysis 沉淀出的方案
```

**命名约定**：Analysis 名称形如 `video-1_profile-x_v1`。其中的 `profile` 指该分析所绑定的 **Keymap**（职业键位方案），与 L4 的 Playbook 无关——早期讨论中两者曾同名为 profile，本文档统一为 **Keymap**（键位）与 **Playbook**（方案）。

**结构上最重要的一刀**：L0–L2 属于 Analysis（**实测**：他这一遍怎么打的）；L3–L4 属于 Project（**知识**：应该怎么打）。

**Segment 与 Lane 是兄弟，不是包含关系**：标记存在于 Lane 上（覆盖整条视频时间轴），Segment 只是**作用范围选择器**，圈定 Agent 分析与导出所处理的时间区间。

Rotation 与 Playbook 是从多个 Analysis 归纳出来的，不属于任何单个片段。这是"流程沉淀"的物理落点。两者都带 `derived_from` 保留溯源，可从方案的任一步跳回其出处录像。

### 5.2 标记（Mark）

两种形态：

- **point mark**：只有一个时刻 + 内容。L1 / L2 默认使用
- **span mark**：有明确起止。L0 的 hold 类使用；人后期精修时也可用

Agent 的一项工作是**把点标记补成区间**：结合 `cast_ms + anim_ms`、相邻标记间隔、L0 侧证据推断 span，并标注置信度。人可将推断的 span 固化为显式区间。

### 5.3 L0 事件与操作

```jsonc
// 事件（原子）
{ "id": "e_041", "t_ms": 12340,
  "kind": "key_down",        // key_down | key_up | mouse_down | mouse_up | wheel
  "key": "2",
  "pos": null,               // 结构保留，本阶段不启用
  "provenance": "human_manual", "confidence": 1.0 }

// 操作（配对合并结果）
{ "id": "a_017", "span": [12340, 12395],
  "kind": "tap",             // tap | hold | chord | wheel | wait
  "target": { "key": "2" },
  "params": { "duration_ms": 55 },
  "source_events": ["e_041", "e_042"] }
```

**坐标结构**（本阶段不启用，保留以备扩展）：同时存归一化 `nx/ny` 与原始像素 `px/py`。原因：录像分辨率与重放分辨率大概率不同，导出脚本必须按归一化坐标乘目标分辨率。

### 5.4 Skill Catalog

管**游戏知识**，与键位无关：

```jsonc
{ "id": "sk_fireball", "name": "火球术", "class": "法师",
  "cd_ms": 6000,
  "cast_ms": 400,       // 前摇：输入到生效
  "anim_ms": 720,       // 动作锁：生效到可接下一个操作
  "cancelable": false,
  "pattern": [ { "op": "tap", "key": "2" } ] }
```

`anim_ms` 至关重要：**动画锁决定了下一个操作最早什么时候能发出**。这个信息不进 IR，后续的时序优化就是瞎猜。

### 5.5 Pattern 语言

**六种 op**：`tap | hold | chord | wheel | gap | skill(ref)`

`skill(ref)` 使 pattern 语言**递归**，从而统一覆盖两种连招形态：键的序列，以及技能的序列。

```jsonc
// 键序列型连招
{ "id": "sk_whirlwind", "name": "旋风连", "class": "战士",
  "cd_ms": 12000, "cast_ms": 150, "anim_ms": 900,
  "pattern": [
    { "op": "tap",  "key": "Q" },
    { "op": "gap",  "ms": 300, "tol_ms": 80 },
    { "op": "tap",  "key": "Q" },
    { "op": "gap",  "ms": 200, "tol_ms": 60 },
    { "op": "hold", "button": "LMB", "ms": 300, "tol_ms": 100 } ] }

// 技能序列型连招
{ "id": "sk_frostfire", "name": "冰火连携",
  "pattern": [
    { "op": "skill", "ref": "sk_fireball" },
    { "op": "gap",   "ms": 300, "tol_ms": 80 },
    { "op": "skill", "ref": "sk_frostbolt" } ] }
```

单键技能是长度 1 的 pattern；组合键是 `[{ "op": "chord", "keys": ["Alt", "3"] }]`。**没有特例，匹配器只有一份代码。**

`tol_ms`（容差）必需——人不可能每次精确 300ms。容差可从多 Take 聚合的方差反推：同一 combo 打 5 遍，第二个 gap 实测 280±40ms，容差就该是 ±40 而非拍脑袋。

### 5.6 Keymap

职业级，管技能 → 输入模式的映射：

```jsonc
{ "id": "km_mage", "version": 3, "class": "法师",
  "binds": { "sk_fireball": ["2"], "sk_blink": ["Shift", "2"] } }
```

**Video 钉住的是 Keymap 的具体版本，不是引用最新版。** 三个月后调了键位，不能让三个月前录的视频的 L1 语义跟着漂移。Keymap 改动 = 新版本；旧 Analysis 继续指向旧版本，需要时手动迁移。

### 5.7 Rotation（L3）

```jsonc
{ "id": "rot_01", "name": "单体稳定输出",
  "params": [ { "name": "填充技", "type": "skill", "default": "sk_fireball" } ],
  "body": [ {"skill":"sk_whirlwind"}, {"gap":180},
            {"skill":"$填充技"},      {"gap":210} ],
  "repeat": { "kind": "until", "note": "直到大招冷却就绪", "executable": false },
  "occurrences": [ { "analysis": "an_07", "span": [21050, 38400],
                     "bindings": { "填充技": "sk_fireball" }, "iterations": 6 } ] }
```

**限制（永久性，除非将来引入画面识别）**：`repeat.until` 的条件在纯操作视角下**不可观测**——只看得见按键，看不见冷却条和血量。条件只能是人写的自然语言注释。IR 中显式标记 `executable: false`，导出器遇到时**必须**生成显式注释，不得假装可执行。

### 5.8 Playbook（L4）

```jsonc
{ "id": "pb_01", "name": "法师单体输出手法 v3", "class": "法师",
  "keymap_ref": { "id": "km_mage", "version": 3 },
  "sections": [
    { "name": "开场爆发", "body": [ {"skill":"sk_frostfire"}, {"gap":400},
                                   {"rotation":"rot_02","iterations":2} ] },
    { "name": "稳定输出", "body": [ {"rotation":"rot_01",
                                   "repeat":"until 目标死亡"} ] },
    { "name": "收尾",     "body": [ ] } ],
  "derived_from": ["an_07", "an_09", "an_12"] }
```

### 5.9 横切字段

每个 IR 元素都带：

| 字段 | 取值 | 用途 |
|---|---|---|
| `provenance` | `human_manual` / `human_edited` / `human_authored` / `agent` / `execution_log` | 随时能问"这条是我标的还是机器猜的"；导出可按来源过滤；`execution_log` 不参与 Take 聚合 |
| `confidence` | `0.0 – 1.0` | 人工标注恒为 1.0；低于阈值的元素在时间轴上以虚线渲染 |

**Note（笔记）**独立于 IR 主体存储，可锚定到任意层的任意元素或任意时间区间。笔记走这条路径，不污染 IR 的机器可读性。

### 5.10 校验器不变式

`ir` 模块提供校验器，任何写入必须通过：

- 同层 span 单调递增；L0 之上允许嵌套但不允许交叉重叠
- 每个 `source_*` 引用必须存在，且被引元素的时间落在本元素 span 内
- 每个 `key_down` 必须有配对的 `key_up`——**未配对显式报错，不静默补全**
- **CD 冲突**：同技能两次间隔 < `cd_ms` → 标记
- **动画锁冲突**：下一操作落在上一技能的 `anim_ms` 之内 → 标记（可能是标错，**也可能是可取消后摇的重要发现**——交人裁定，不当错误吞掉）

**层间包含关系不是写入期不变式。** 因为 L0/L1/L2 是三条**独立的人工观察通道**（见 3.1），它们在标注时彼此无从属关系，`L1.span ⊇ ∪ L0.span` 这类关系只有在 Agent 跨层对齐**之后**才成立。因此它属于**对齐后的一致性检查**，产出的是待裁决冲突项（见 7.6），不是阻止写入的校验规则。

## 6. 标注工作台

### 6.1 主界面

```
┌───────────────────────────────────────────┬──────────────┐
│  视频播放器                                 │  右侧面板     │
│  0.25× / 0.5× / 1×                        │  ├ 录入       │
│  逐帧步进 [ ]                              │  ├ Agent 会话 │
│                                           │  ├ 笔记       │
│                                           │  └ 导出预览    │
├───────────────────────────────────────────┴──────────────┤
│  打表计时条   当前 00:21.437   Δ 上一标记 176ms   [T 打点]  │
├──────────────────────────────────────────────────────────┤
│  缩略图带 ▓▓▓▓▒▒▒▓▓▓▓▓▒▒▓▓▓   ← 进度同步 · 拖拽圈选         │
├──────────────────────────────────────────────────────────┤
│  L2  ├── 冰火连携 ──┤                                     │
│  L1  ● 火球术   ● 冰锥   ● 拾取                            │
│  L0  ├tap 2┤  ├tap 3┤  ├hold F 300ms┤                    │
└──────────────────────────────────────────────────────────┘
```

泳道可独立折叠。选中某条泳道后，录入操作作用于该泳道的当前 Take。

### 6.2 标注流程

```
1. 加载视频 → 新建 Analysis「video-1_profile-x_v1」
2. 选 L0 泳道 → 0.5× 播放，缩略图上进度同步移动 → 空格暂停
   → 在 L0 泳道的当前时间轴位置录入操作（左键单击 / hold 开始 / …）
   → 完成 Take #1
3. 重复步骤 2 产出 Take #2、#3 …        ← 多次独立测量
4. 切到 L1 泳道 → 同样方式打点标技能名   ← 可多 Take
5. （可选）切到 L2 泳道 → 打点标 combo   ← 可多 Take
6. 触发 Agent 推断
7. 切换抽象粒度查看与编辑（L0…L4 任一粒度）→ 人做最终质量调优
```

### 6.3 录入交互

- **主路径**：暂停 → 右侧面板下拉选择（L1/L2 显示技能名，L0 显示操作类型 + 键）→ 选类型与时长 → 确认插入到当前帧
- **加速层**（可选，走同一条命令路径，不影响数据模型）：面板中每项挂快捷键，直接敲即插入；`[` `]` 逐帧步进；`,` `.` 微调选中标记 ±10ms

### 6.4 编辑能力

- **区间平移**：框选一段 → 整体 ±N ms。应对系统性偏移，比逐个改快一个量级
- **实时校验渲染**：CD 冲突、动画锁冲突、未配对 hold、未定义技能引用 → 立即标红
- **置信度渲染**：Agent 产出且置信度低于阈值的元素以虚线绘制
- **不确定度渲染**：多 Take 聚合后方差大的位置绘制**加宽阴影带**——那是你自己每遍都标不一致的位置，也是最该慢放复核的位置
- **笔记锚定**：选中任意元素或框选任意区间，`N` 键加笔记

### 6.5 打表计时工具

独立于标注的测量工具条：

- 当前时间码常驻显示，**ms 精度**
- 时间轴上任意两个相邻标记之间**自动显示 Δms**（无需选中）
- **打表模式**：`T` 键打一个测量 marker，连续两下即显示间隔。marker 独立于 IR 存储，是纯测量草稿，可随时清空
- 选中任意两个 marker 或两个 IR 元素 → 显示精确间隔，**一键回填到 Skill Catalog**（量出火球术动作 720ms → 直接写进 `anim_ms`）

**回填是重要的沉淀机制**：Skill Catalog 不需要预先填好，你边分析边把游戏常量测出来沉淀进去。标的视频越多，这张表越准，后续自动推导与校验就越强。

### 6.6 片段圈选

Segment 是**分析的作用域单位**——Agent 分析、导出、注入都以 Segment 为单位。一个视频可划多个 Segment，允许重叠（同一段操作可从"连招"和"资源管理"两个角度各分析一次）。

## 7. Agent 分析层

### 7.1 职责边界

```
输入：Analysis 的 L0–L2 泳道数据 + Skill Catalog + Keymap
输出：对齐结果 + Rotation 提案 + Playbook 提案（均为提案，不直接写入）
禁止：读画面、猜游戏状态、推断不可观测量
```

### 7.2 推断阶段的六个子任务

| # | 任务 | 承担者 |
|---|---|---|
| a | **泳道内多 Take 聚合** → 稳健时序 + 不确定度 | 算法（序列对齐取中位数，IQR 作不确定度） |
| b | **跨层对齐** L0 ↔ L1 ↔ L2 | 算法为主，歧义处 LLM 辅助 |
| c | **Keymap 反推 / 校验** | 算法（统计共现） |
| d | **点标记补全为区间** | 算法（`cast_ms`+`anim_ms`+相邻间隔）+ 置信度 |
| e | **L3 循环归纳** | 算法找候选 + LLM 命名 + 匹配器验证 |
| f | **L4 方案编排** | LLM 提案 + 人裁决 |

### 7.3 混合架构：重复模式的发现不交给 LLM

| 阶段 | 承担者 | 理由 |
|---|---|---|
| 候选发现 | **确定性算法**（后缀自动机 / 最长重复子串 / n-gram 频次） | 找重复子序列，算法比 LLM 准、快、且**可复现**——同一输入永远给同一批候选 |
| 解释与命名 | **LLM** | 把 `[旋风连, gap180, 火球术] × 6` 命名为"单体稳定输出"、判断哪个位置是可替换参数、写出人能读的说明 |
| 验证 | **确定性匹配器**（复用已有实现） | 见 7.5 |
| 裁决 | **人** | 最终质量调优 |

流水线：`算法找候选 → LLM 解释命名 → 匹配器验证 → 人裁决`

### 7.4 匹配器规则

- **最长优先匹配**：从每个位置尝试所有 pattern，取匹配长度最长者
- **自底向上多趟**：先匹配纯操作 pattern 产出 L1，再在"L1 + 剩余操作"的混合序列上匹配含 `skill` op 的 pattern 产出 L2，直到不动点
- **歧义不自动猜**：两个等长 pattern 都匹配时标记为歧义，时间轴上高亮交人裁决，裁决结果记入 IR（`provenance: human_manual`）
- **匹配失败保留为 `unmatched`** 并在时间轴上标出

### 7.5 可证伪的验证报告

每个提案必须附带验证报告。Agent 提出的是**假设**，由匹配器回放到原始数据上验证：

```
提案 · 单体稳定输出循环
  body : [旋风连, gap 180, 火球术, gap 210]
  声称覆盖 : an_07 [21050 → 38400]
  ────────────────────────────────────────
  验证报告（确定性匹配器回放）
  ✓  6 次迭代中完整匹配 5 次
  ⚠  第 4 次迭代 gap 实测 340ms，超出容差 ±60
  ⚠  21050 之前有 2 个 unmatched 操作未被覆盖
  覆盖率 88%
```

Agent 拿到报告后**自我修正并重新提案**——这就是"反复校验"：`提案 → 验证 → 修正` 循环，收敛或超过 N 轮后交给人。

三个好处：Agent 输出不再是"看起来合理的散文"而是**经过确定性验证的结构**；验证器复用已有匹配器**无需新造**；覆盖率是客观数字，一眼判断提案值不值得看。

### 7.6 冲突与异常是高价值输出，不是噪声

系统必须把以下情况**作为发现推给人**，而非过滤掉：

**三方冲突**（跨层对齐的必然产物，纯人工分析拿不到）：
```
⚠ t=21.4s   L0 标注「按键 2」· L1 标注「冰锥」· Keymap 记录「2 = 火球术」
   → 三者不一致。可能是：L0 标错 / L1 标错 / Keymap 过期 / 这一版改过键位
```
裁决一次，同时修正标注与 Keymap。**Keymap 就是这么越用越准的。**

**其他信号**：
- 反复出现的 `unmatched` 操作序列 → Catalog 里缺一条技能/连招定义
- 某次迭代 gap 显著偏离 → 那一次可能是操作失误或遭遇打断，值得回看
- 动画锁冲突 → 可能是**可取消后摇**的攻略发现

### 7.7 提案机制与编辑保护

- Agent 产出的是**提案（Proposal）**，不直接写入 Rotation / Playbook
- 提案以**块级 diff** 呈现，人逐块 `接受 / 拒绝 / 改了再接受`
- 每个块记 `provenance`
- **人改过的块自动 pinned**，Agent 后续重跑视为不可动区域，除非人手动解锁
- Playbook 有版本链，任何一次接受都可回滚

这套机制让 Agent 可以**无限次重跑而人的编辑永远安全**——这是敢让 Agent 反复校验的前提。

## 8. L3 / L4 块编辑器

### 8.1 核心架构约束

> **编辑器的块类型 = IR 的节点类型。编辑器是 IR 的直接视图，脚本是只读的派生产物。系统永远不反向解析脚本。**

这条约束立住后，"编辑脚本"的需求自然消失：脚本随时可见、且永远与 IR 同步。

### 8.2 界面

```
┌─ Playbook: 法师单体输出手法 v3 ───────── [Keymap: km_mage v3] ──┐
│                                                                │
│ ▼ 开场爆发                                        [+ 段落]      │
│   ┌─────────────┐ ┌── 400ms ──┐ ┌──────────────────┐          │
│   │ 冰火连携      │ │   等待     │ │ ⟳ 爆发循环 × 2    │          │
│   │ Q→300→Q→LMB │ │ 实测 412±31│ │  填充技 = 火球术 ▾ │          │
│   └─────────────┘ └───────────┘ └──────────────────┘          │
│                                                                │
│ ▼ 稳定输出                                                      │
│   ┌────────────────────────────────────────────────┐          │
│   │ ⟳ 单体稳定输出   直到「目标死亡」  ⚠ 不可执行       │          │
│   │   ├ 旋风连                              [来源 ↗] │          │
│   │   ├ 等待 180ms   实测 176±22ms · 12次观测  [采纳] │          │
│   │   └ 火球术                                      │          │
│   └────────────────────────────────────────────────┘          │
└────────────────────────────────────────────────────────────────┘
```

### 8.3 块词汇表（与 IR 节点一一对应，不多不少）

| 块 | 对应层 | 可编辑内容 |
|---|---|---|
| 技能块 | L1 / L2 | 换技能（从 Catalog 下拉） |
| 操作块 | L0 | 键 / 按钮、类型、时长——用于 Catalog 未定义的杂项 |
| 等待块 | L0 | 时长，旁边常驻实测分布 |
| 循环块 | L3 | 参数绑定、重复次数或条件注释；可嵌套、可折叠 |
| 段落块 | L4 | 命名与折叠 |
| 注释块 | — | 人写的说明，导出时编译成脚本注释 |

### 8.4 交互

按投入优先级排序：

1. **块级 diff 与逐块裁决**（主通道——Agent 生成初稿 + 人做最终调优）
2. **就地编辑**：点技能名弹 Catalog 下拉；点时长弹数字输入，旁边显示实测分布
3. **实测值采纳**：等待块显示 `标称 180ms · 实测 176±22ms · 12次观测`，一键把实测中位数写入
4. **实时校验**：CD 冲突、动画锁冲突、未定义引用，编辑时立即标红，不等到导出才报错
5. **导出预览并排**：右侧实时渲染编译出的 AHK / Markdown，改一个块立刻看到脚本变化
6. **拖拽重排**：块与块之间
7. **反向溯源**：点任意块的 `[来源 ↗]`，时间轴跳到其出处片段并高亮（基于 `derived_from`）
8. **从时间轴拖入**（次要通道）：标注时间轴上框选一段拖进编辑器变成块序列。做基础形态即可，不做多选 / 自动折叠等高级能力

## 9. 导出与执行

### 9.1 导出后端

每个后端签名 `IR → bytes`，一个文件一个后端：

| 后端 | 产物 | 用途 |
|---|---|---|
| `md` | Markdown 流程文档 | 攻略沉淀、人读 |
| `ahk` | AutoHotkey v2 脚本 | 主力执行路径 |
| `razer` | Razer Synapse 宏 | 硬件宏路径 |
| `plan` | 注入计划 JSON | 内置执行器 |

**可从任意层导出**：L4 → 完整方案脚本；L3 → 单个循环；Segment → 该段的原样复现。

### 9.2 编译规则

1. 时间一律用**多 Take 聚合的实测中位数**，不用 pattern 标称值。标称值用于识别，实测值才是这个操作者真实的节奏——而复现节奏正是目的
2. Rotation → AHK function；固定次数 → `Loop N`
3. `executable: false` 的条件循环 → 编译为 `Loop { }` + 显式注释说明进出条件由人判断，**并在文件头汇总列出所有此类位置**
4. 低置信度元素 → 编译为**注释掉的行 + 警告**，绝不静默包含
5. 坐标（若将来启用）→ 归一化值 × 目标分辨率，脚本头部声明基准分辨率

### 9.3 注入执行器

- 消费 `plan` JSON，**仅 Windows**，起步走 AHK 子进程
- 控制台：开始 / 暂停 / 停止 / 单步
- **全局急停热键必须实现**（如 F12 立即停止并释放所有按住的键）——安全底线，非可选项
- **只执行，不判断成败**——正确性由人肉眼判断
- **执行日志回灌**：实际发出的事件流按 Take 格式导入回 Analysis 的 **L0 泳道**（`provenance` 标为 `execution_log`，不参与多 Take 聚合的中位数计算），与人工标注并排显示。零额外成本（格式本就一致），但让"我以为的"与"实际跑的"可直接对比

**合规说明**：目标为第三方商业游戏、个人自用场景。带反作弊的商业游戏通常会忽略 `SendInput` 级别的合成输入，因此**注入是允许失败的可选后端，不是主路径**；IR + 脚本/宏导出才是主路径。是否符合目标游戏的用户协议由使用者自行判断。

## 10. 错误处理

> **编辑期宽松，导出期严格。**

允许标注过程中留下不合法状态（未配对的 hold、引用了尚未定义的技能），校验器只在 UI 标红提示，不阻塞编辑。**导出时必须全部通过校验，或由人逐条显式确认忽略。**

| 类型 | 处理 |
|---|---|
| 数据不一致 | 校验器捕获 → UI 标红 → 不阻塞编辑 |
| Agent 失败 / 超时 | 返回空提案 + 错误说明。`agent` 是纯函数 `IR → Proposal`，**失败无副作用**，已有数据绝不受损 |
| 宿主 / 执行失败 | `HostAdapter` 抛结构化错误（设备不可用 / 权限不足 / 注入被拒）+ 处置建议 |

## 11. 测试策略

| 目标 | 方式 |
|---|---|
| `ir` 校验器 | **属性测试**：生成随机 IR，验证不变式恒成立 |
| 匹配器 / 对齐器 | **黄金样例集**：手工构造 Analysis 标注数据 + 期望输出，回归比对 |
| **Agent 层** | **评测集**：一组标注完整、人工确认过 Rotation / Playbook 的 Analysis。跑 Agent 算覆盖率与一致性。**任何 prompt 改动必须过这个集**——否则调 prompt 就是赌博 |
| `emit` 后端 | **快照测试**：`IR → 脚本文本`，diff 比对 |
| `HostAdapter` | MockHost 保证全链路在 macOS 上可测；Windows 真实注入只能手工验证 |
| 前端 | 时间轴编辑器核心操作的组件测试 |

具体测试用例与评测集构造方式留到实施计划阶段。

## 12. 里程碑

四个里程碑体量不小（Python 后端 + React 前端 + 平台适配）。**实施计划按里程碑分别编写，一次一个**——M1 跑通后对标注效率的实感会改变 M2 的很多细节。

### M1 · 标注可用（最小闭环）

`ingest`（上传 + URL 拉取）· `media`（解帧 / 缩略图带）· 播放器 + 泳道时间轴 · L0/L1 打点标注 · Take 多版本与聚合 · SQLite 持久化 · 打表计时工具

**验收**：完整标完一个视频，关闭重开数据仍在。

### M2 · 对齐与推断

Skill Catalog / Keymap 编辑界面 · 跨层对齐 · Keymap 反推 · 三方冲突清单 · 点标记补区间 · Agent 循环发现（算法候选 → LLM 命名 → 匹配器验证）

**验收**：从一份标注产出带覆盖率验证报告的 Rotation 提案。

### M3 · 方案与导出

块编辑器（L3/L4）· 提案 diff 与逐块裁决 · `md` + `ahk` 导出

**验收**：从一个视频走到一份可读文档 + 一个能运行的 AHK 脚本。

### M4 · 执行与采集

WindowsHost 采集 + 注入 · 执行控制台 + 急停 · 执行日志回灌 · `razer` 导出

**验收**：Windows 上注入跑通，日志能回灌对比。

**M1–M3 是主干，M4 是外围。** 采集放最后，因为上传 + URL 已能覆盖现有工作方式。

## 13. 已知限制

1. **循环条件不可执行**。纯操作视角下看不见游戏状态，进出循环的时机只能靠人判断。解除此限制需引入画面识别，那是一次独立的重大决策。
2. **L0 是推断而非观察**。视频里看不见键盘，L0 标注依赖分析师的键位知识，天然带误差。这正是需要多 Take 聚合与跨层对齐校验的原因。
3. **注入可能被目标游戏拒绝**。合成输入在带反作弊的商业游戏中常被忽略。注入是可选后端。
4. **Razer 宏格式**未在设计阶段验证，实施时需先确认其导入格式规格。
5. **走位 / 瞄准类操作不支持**。数据模型保留坐标结构，但匹配、编辑、导出链路均未覆盖。
